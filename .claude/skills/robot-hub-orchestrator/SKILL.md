# 통합 로봇 허브 오케스트레이터

## 실행 모드: 혼합 (서브에이전트 위임 + 생성·검증 반복)
작업 목록(로봇 4대)과 순서가 정해져 있고, 에이전트끼리 대화할 필요 없이 파일로 결과를 넘기면 되므로 서브에이전트를 쓴다. 메인(이 스킬을 실행하는 에이전트)이 단계 사이에서 사용자 승인과 QA 반복을 관리한다.

## 에이전트 구성
| 역할 | `subagent_type` | 스킬 | 산출물 |
| --- | --- | --- | --- |
| 인벤토리(로봇당 1명) | `robot-inventory-analyst` | robot-inventory | `_workspace/01_inventory_{id}.json` |
| 레포 게시 | `repo-publisher` | github-repo-publish | `_workspace/02_publisher_report.md` |
| 애니메이터 | `robot-motion-animator` | robot-motion-animation, hub-shell(규격) | `hub/robots/{id}.js`, `_workspace/03_animator_motions.md` |
| 허브 엔지니어 | `hub-web-engineer` | hub-shell | `index.html`, `hub/*`, `start_hub.bat`, `_workspace/04_engineer_notes.md` |
| QA | `hub-qa` | hub-qa-check | `_workspace/05_qa_report.md` |

로봇 id와 폴더: `smars`→`smars_web`, `ottobot`→`ottobot`, `robotdog`→`robot_dog`, `bike`→`self-balancing-bike_app`.

## 작업 절차

### 0단계: 기존 작업 확인
- `_workspace/`가 없으면 → 1단계부터.
- 있고 부분 수정 요청(예: "바이크 애니메이션만", "복귀 시간 5분으로")이면 → 해당 담당만 재호출하고 이전 산출물 경로와 사용자 피드백을 프롬프트에 넣는다. 그다음 5단계 QA는 항상 다시 돈다.
- 있고 새 로봇·새 요구가 들어왔으면 → `_workspace/`를 `_workspace_{YYYYMMDD_HHMM}/`로 옮기고 처음부터.
- 단순 설정값 변경(`idleMs` 등)은 메인이 `hub/robots.config.js`를 직접 고치고 정적 검사만 돌린다.

### 1단계: 인벤토리 (서브에이전트 4명 병렬)
한 메시지에서 `robot-inventory-analyst`를 로봇마다 하나씩 4번 호출한다. 프롬프트: 로봇 id, 폴더, 출력 경로, "로봇 폴더는 읽기만 할 것".
결과를 받으면 메인이 4개 JSON을 읽고 확인한다: 제어 웹 경로가 실제로 있는가, 정지 방법이 있는가, `repo.status`. 비어 있는 핵심 항목(`control_page`, `stop`)은 사용자에게 물을 질문 목록으로 모은다.

### 2단계: 사용자 승인 (메인)
AskUserQuestion으로 한 번에 묻는다:
1. `repo.status`가 `local-only`/`none`인 로봇 + 허브: 레포 이름·public/private, 커밋 안 된 변경 포함 여부
2. GitHub Pages를 켤지(같은 출처로 온라인 허브 운영. public 필요)
3. 1단계에서 모인 질문(제어 웹 후보가 여럿인 경우 등)
4. 무입력 복귀 시간(기본 3분 + 경고 15초)

레포 게시를 거절하면 3단계를 건너뛰고 로컬 허브만 만든다.

### 3단계: 레포 게시 (서브에이전트 1명, 승인 시)
`repo-publisher`에 승인 내용을 그대로 적어 호출한다. 허브 레포의 서브모듈 등록은 로봇 레포가 모두 생긴 뒤여야 하므로 같은 에이전트가 순서대로 처리한다. 허브 파일이 아직 없으면 허브 레포 생성은 6단계로 미룬다.

### 4단계: 허브 제작 (서브에이전트 2명 병렬)
한 메시지에서 `robot-motion-animator`와 `hub-web-engineer`를 함께 호출한다. 두 산출물은 `hub-shell`의 `RobotHub.register` 규격으로만 만나므로 병렬로 만들 수 있다. 프롬프트에 인벤토리 경로 4개, 2단계에서 정한 설정값, 담당 파일 범위를 적는다(서로의 파일을 건드리지 않는다).

### 5단계: QA 반복 (최대 3회차)
1. `hub-qa` 호출 → `_workspace/05_qa_report.md`.
2. 실패가 없으면 6단계로.
3. 실패가 있으면 담당별로 나눠 `robot-motion-animator`/`hub-web-engineer`를 병렬 재호출(보고서 경로 + 해당 결함 번호만 고치라고 지시) → 다시 1.
4. 3회차에도 **높음** 결함이 남으면 멈추고 사용자에게 보고한다. 낮음·중간은 남은 목록으로 보고하고 진행한다.

### 6단계: 마무리 (메인)
1. 브라우저로 직접 확인하도록 `start_hub.bat` 실행 방법을 안내한다.
2. 승인된 경우 허브 레포 생성·push를 `repo-publisher`에 맡긴다(3단계에서 미룬 경우).
3. `HANDOFF.md`를 갱신한다(현재 상태 표, 로봇별 정보, 다음 할 일, 미해결, 변경 기록).
4. `CLAUDE.md` 변경 이력에 이번 실행으로 바뀐 하네스 구성이 있으면 적는다(허브 산출물 변경은 적지 않는다).
5. 사용자 보고: 만든 파일, 로봇별 선택 동작, 정지 방식(같은 출처 정지 / iframe 제거만), 레포 URL, 사람 확인 필요 항목(실물 로봇 정지 시험).

## 데이터 전달
모두 `_workspace/` 파일로 넘긴다(`{단계}_{담당}_{산출물}`). 최종 산출물만 `통합/` 루트와 `hub/`에 둔다. `_workspace/`는 `.gitignore`에 넣고 지우지 않는다.

## 안전 규칙
- 허브 에이전트는 로봇에 명령을 보내지 않는다. 실물 시험은 사람이 한다.
- 로봇 폴더 파일은 수정하지 않는다. 필요하면 해당 로봇 하네스로 넘기라고 사용자에게 보고한다.
- 외부 공개(레포 생성·push·Pages)는 2단계 승인 범위 안에서만.

## 오류 처리
| 상황 | 대응 |
| --- | --- |
| 인벤토리 1대 실패 | 1회 재호출. 또 실패하면 그 로봇은 "준비 중" 구획으로 두고 보고서에 적는다 |
| `gh` 인증 만료·권한 거부 | 재시도하지 않는다. 사용자에게 `! gh auth login` 안내 후 대기 |
| 사용량 한도 소진 | 재시도하지 않는다. 부분 산출물을 직접 열어 진행 범위를 확인하고 `_workspace/00_status.md`에 기록, 풀리는 시각과 함께 보고 |
| 비밀 값 검사 걸림 | push 중단, 파일:줄만 보고(값은 보고하지 않음) |
| 정지 방법을 못 찾은 로봇 | 허브는 iframe 제거만으로 복귀하고, 화면과 보고서에 "수동 정지 확인" 표시 |
| 에이전트 판단 기록이 비어 있음 | 메인이 추측해 채우지 않는다. 해당 에이전트를 재호출해 기록하게 한다 |

## 테스트 시나리오
### 정상 흐름
1. "4대 통합 허브 만들어줘" → 인벤토리 4건 병렬 → ottobot·robot_dog가 `local-only`로 나옴.
2. 사용자가 둘 다 public, Pages 켬, 복귀 3분 승인 → 레포 2개 생성.
3. 애니메이터·엔지니어 병렬 → QA 1회차 실패 2건(자막 7자, 정지 선택자 오타) → 담당별 재호출 → 2회차 통과.
4. 허브 레포 생성·서브모듈 등록 → `start_hub.bat`으로 열면 4구획 애니메이션, 구획 클릭 시 제어 웹, 3분 무입력 시 경고 후 복귀.

### 오류 흐름
1. robot_dog 인벤토리에서 제어 웹 후보 2개, 정지 버튼 미확인.
2. 2단계 질문에 후보 선택을 넣고, 정지는 `null`로 둔다.
3. QA가 "robotdog 정지 방법 없음"을 높음이 아닌 "사람 확인 필요"로 분류(허브가 명령을 보낼 수 없고 iframe 제거로 연결이 끊김). 보고서와 화면에 수동 정지 안내.
